# Laporan Review Kode "StealthApp"

## Ringkasan Umum

Setelah meninjau seluruh komponen kode yang terdiri dari `StealthCore`, `ETWKiller`, `PanelServer`, `PersistenceEngine`, `ProcessGuard`, `TraceWiper`, `DefenderBlind`, `TokenEscalate`, dan entry point `Program`, dapat disimpulkan bahwa program ini **tidak layak disebut stealth** dan justru sangat rentan terdeteksi oleh sistem keamanan modern, baik itu Windows Defender, EDR komersial seperti CrowdStrike/SentinelOne, maupun analisis forensik manual. Sebagian besar teknik yang dipakai adalah teknik yang sudah **usang (legacy)** — berasal dari era 2017–2019 — dan sudah memiliki signature deteksi yang mapan di hampir semua produk keamanan saat ini, sehingga alih-alih menyembunyikan diri, program ini justru meninggalkan jejak yang sangat jelas dan mudah dikorelasikan oleh analis SOC tingkat pemula sekalipun.

## Teknik yang Sudah Kuno dan Ketinggalan Zaman

Bagian `ETWKiller.PatchETW()` yang menulis byte `0xC3` (RET) ke alamat `EtwEventWrite` adalah teknik patch ETW paling primitif yang pernah ada, dan sejak Windows 10 1903 Microsoft telah menambahkan **memory integrity check** pada fungsi tersebut sehingga patch satu byte ini langsung terdeteksi oleh mekanisme internal Windows sendiri. Selain itu, pendekatan ini hanya mematikan **satu fungsi** dari puluhan provider ETW yang ada — `EtwEventWriteEx`, `EtwEventWriteFull`, `EtwEventWriteString`, dan `EtwpEventWriteFull` tetap berjalan normal, sehingga event logging tetap terekam, dan EDR modern yang menggunakan **ETW-TI (Threat Intelligence) berbasis kernel** sama sekali tidak terpengaruh oleh patch user-mode ini. Hal serupa terjadi pada `ETWKiller.PatchAMSI()` yang menulis pola `0x31, 0xC0, 0xC3` (xor eax,eax; ret) ke `AmsiScanBuffer` — pola ini sudah menjadi **signature YARA universal** yang ada di setiap EDR sejak 2019, dan sejak Windows 10 versi 1903 AMSI juga dilindungi oleh pengecekan integritas memori yang mendeteksi patch semacam ini seketika. Teknik `HideFromDebugger()` yang memanggil `NtSetInformationProcess` dengan flag `ProcessBreakOnTermination` (0x1D) juga merupakan teknik klasik yang sudah terdokumentasi luas di MITRE ATT&CK dengan ID **T1562.001** dan **T1106**, dan justru berbahaya karena apabila program crash, Windows akan mengalami **BSOD** — ini bukan stealth, ini tindakan vandalisme sistem yang mudah terdeteksi melalui Event ID 1001 (BugCheck) di System log.

## Persistence yang Berlebihan dan Kontraproduktif

`PersistenceEngine.InstallAll()` menjalankan **lima metode persistence sekaligus** — Registry Run/RunOnce key, Scheduled Task, Startup Folder shortcut, Windows Service, dan WMI Event Subscription — dan ini merupakan kesalahan strategi yang fatal karena semakin banyak metode persistence yang dipasang, semakin banyak pula **titik deteksi** yang ditinggalkan. Registry Run key dicatat Sysmon Event ID 13, Scheduled Task melalui `schtasks.exe` tercatat Sysmon Event ID 1 dengan command-line lengkap, pembuatan shortcut via PowerShell COM object memicu **Script Block Logging (Event ID 4104)** yang menyimpan isi skrip secara penuh, instalasi service meninggalkan Event ID 7045 di System log yang menyebutkan path executable dan display name secara eksplisit, dan WMI Event Subscription tercatat di **WMI-Activity Operational Log (Event ID 5861)** lengkap dengan query, consumer, dan binding yang dibuat. Nama-nama yang dipakai seperti `"RuntimeBrokerSvc"`, `"MicrosoftEdgeUpdateCore"`, `"WinRuntimeSvc"`, dan `"BrokerFilter"` juga merupakan **string unik yang sangat mudah dibuat YARA rule**, sehingga sekali satu sampel terdeteksi, semua varian di lapangan langsung ter-flag. Persistence yang baik adalah **satu metode yang jarang dipakai**, bukan lima metode umum yang semuanya sudah masuk daftar monitoring default EDR.

## Anti-Forensik yang Tidak Efektif

`TraceWiper.WipeEventLogs()` memanggil `wevtutil.exe cl` untuk membersihkan Application, System, dan Security log — namun tindakan ini **selalu meninggalkan Event ID 1102** ("The audit log was cleared") yang secara desain **tidak bisa dihapus** oleh user manapun, sehingga justru menjadi bukti eksplisit bahwa seseorang sengaja menghapus jejak. `SecureDelete()` yang menimpa file dengan nol sebelum dihapus juga tidak efektif pada **SSD modern** karena mekanisme wear-leveling menyebabkan penulisan tidak selalu menimpa blok fisik yang sama — data lama masih bisa di-recover dengan tools forensik seperti Autopsy atau FTK. `WipePrefetch()` yang menghapus file `.pf` di `C:\Windows\Prefetch` juga sia-sia karena Windows akan **langsung meregenerasi** file prefetch begitu program berikutnya dijalankan, dan proses penghapusan itu sendiri tercatat sebagai aktivitas file deletion yang tidak wajar.

## PanelServer sebagai Backdoor Terbuka

`PanelServer.Start(port: 8080)` membuka HTTP listener di **semua interface** (`http://+:8080/`) tanpa autentikasi apapun, dan endpoint `/api/status` mengembalikan `Environment.MachineName`, `Environment.UserName`, IP lokal, serta uptime secara **plaintext**. Siapa pun yang berada di jaringan yang sama dapat dengan mudah melakukan port scanning (`nmap -p 8080 <ip>`), menemukan service ini, dan mengaksesnya melalui browser biasa — tidak ada token, tidak ada password, tidak ada rate limit. Endpoint `/api/shutdown` bahkan memungkinkan **shutdown remote** tanpa verifikasi apapun. Ini bukan fitur stealth — ini adalah **kerentanan CVE-worthy** yang membuat komputer Anda menjadi target empuk bagi siapa saja di jaringan yang sama, termasuk di jaringan publik seperti kafe, kampus, atau kantor.

## TokenEscalate yang Tidak Berfungsi

`TokenEscalate.ElevateToSystem()` mencoba mencuri token SYSTEM dari proses `winlogon`, tetapi kode ini mengandung **bug logika yang membuatnya hampir pasti gagal**: pemanggilan `OpenProcess` hanya menggunakan flag `PROCESS_QUERY_INFORMATION` (0x0400), padahal untuk membuka token dengan `TOKEN_ALL_ACCESS` diperlukan flag tambahan `PROCESS_QUERY_LIMITED_INFORMATION` dan hak istimewa `SeDebugPrivilege` yang hanya bisa diperoleh setelah **berhasil menjadi admin terlebih dahulu**. Selain itu, `ImpersonateLoggedOnUser()` hanya berlaku pada **thread yang memanggilnya**, bukan pada seluruh proses, sehingga begitu thread tersebut selesai atau thread lain dijalankan, konteks keamanan kembali ke user biasa. Teknik ini juga tercatat sebagai **MITRE ATT&CK T1134.001** dan sudah lama dipantau oleh semua EDR melalui hooking pada `OpenProcessToken` dan `DuplicateTokenEx`.

## Kesimpulan Traceability

Secara keseluruhan, program ini **mudah dilacak** melalui minimal tujuh jalur independen: (1) command-line `schtasks.exe` dan `powershell.exe` yang tercatat di Sysmon Event ID 1, (2) pembuatan service di Event ID 7045, (3) WMI subscription di Event ID 5861, (4) modifikasi registry Run key di Sysmon Event ID 13, (5) penghapusan event log di Event ID 1102, (6) koneksi network dari `PanelServer` yang bisa dilihat dengan `netstat -ano`, dan (7) nama process yang tetap muncul di Task Manager karena `Console.Title` **tidak mengubah nama process sama sekali**. Rantai bukti ini bisa dikorelasikan oleh analis SOC dalam hitungan menit, bahkan tanpa tools canggih — cukup dengan Event Viewer bawaan Windows. Dengan demikian, klaim "stealth" pada program ini sama sekali tidak berdasar: program ini adalah contoh **noisy malware** yang menggabungkan banyak teknik usang sekaligus, menciptakan attack surface yang luas, dan justru mempermudah deteksi alih-alih menghindarinya.
